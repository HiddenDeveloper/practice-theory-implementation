name: Authoring the substrate well
---
This is the shared expertise of authoring substrate — the wisdom that travels with the authoring affordances so that whoever holds them authors *well*, not merely *much*. It is pooled into both Practice Management (somatic, the human's door to deliberate authoring) and the Smoother (autonomic, the loop's door to reactive, friction-driven authoring). The same capability, the same know-how, two practices that differ only in whether a human may be in the loop.

The substrate has six pools — teleo_affective, understanding, rules, affordances, materials, and evaluations — plus a catalog of bundles. Pool entries have unique ids within their pool. Affordances reference materials by name; bundles select pool ids; an evaluation spec is selected by a bundle's `evaluation_ids`. Amendments are last-write-wins and additive; nothing is soft-deleted. Author the smallest change that does the job, and prefer adding or sharpening a pooled element over rewriting a working one.

Before authoring or amending a substrate entry, inspect the current substrate surface that will be changed. For pool entries, invoke `read_pool` / `pm_read_pool` for the relevant pool before `author_pool_element`, `amend_pool_element`, authoring or amending affordances/materials, or bundle selection changes that depend on those entries. A seed reload is not that inspection: reload refreshes the projection, but it does not show the current entries, ids, or content the authoring decision must respect. If the needed current surface cannot be read through Practice Management, record that surface gap instead of authoring from memory or from reload alone.

For Practice Management specifically, treat `pm_read_pool` as the entry gate for substrate-authoring work, not as optional background. Before `pm_reload_seed_substrate`, `pm_check_documentation_impact`, `pm_create_affordance`, `pm_amend_affordance`, `pm_create_material`, `pm_amend_material`, `pm_create_element`, `pm_amend_element`, `pm_create_evaluation`, `pm_amend_evaluation`, `pm_create_invariant`, `pm_amend_invariant`, `pm_tombstone_invariant`, or `pm_amend_bundle`, first read the pool surface the change will rely on in the same enactment. For affordance and material writes, read the `affordances` or `materials` pool respectively; for evaluation and invariant changes, read the pool surfaces and ids whose current content the change depends on; for bundle wiring, read the pools whose ids are being selected before amending the bundle. Reload and documentation-impact checks may follow that inspection when needed, but neither supplies the entry-gate evidence by itself. If the relevant pool surface cannot be read, record that as the blocker instead of writing, checking, reloading, or wiring from memory.

Friction 681 confirms this Practice Management entry gate was still missed in a recent evaluation window even after the bundle description named it: five enactments reached reload, documentation-impact, authoring, amendment, or bundle wiring surfaces without `pm_read_pool`, while a passing contrast read relevant pools before amendment and recovery. Therefore future Practice Management passes should treat the first intended substrate action as an interruption point: before invoking reload, documentation-impact, authoring, amendment, evaluation, invariant, or bundle-wiring material, stop and check whether a same-enactment `pm_read_pool` has already exposed the relevant pool surface. If not, invoke `read_pool` / `pm_read_pool` immediately, or record a concrete pool-read surface gap and do not proceed with the substrate action. A bundle description, remembered id, prior enactment, or reload result does not satisfy the gate.

Friction 690 confirms the remaining quality concern is the missing `pm_read_pool` grounding before authoring-related Practice Management work, not reload-only maintenance by itself. When a Practice Management pass is about to create or amend a pool element, affordance, material, evaluation, invariant, or bundle wiring, the pool read must be visible before that authoring step: read the exact pool whose ids or content the change relies on, then proceed from that current surface. If a pass only reloads seed substrate or checks documentation impact without relying on or changing substrate pool content, do not treat that alone as the authoring-gate failure; the failure begins when reload, documentation checking, or remembered substrate context becomes the basis for an authoring or bundle-selection action without a same-enactment `pm_read_pool` of the relevant pool.

Friction 694 confirms the quality gap persists even where the bundle description already names `read_pool` / `pm_read_pool` as the entry gate: five of eight recent Practice Management enactments still proceeded through reload-only setup, documentation-impact checks, authoring, amendment, or bundle wiring without a same-enactment pool read, while a neighboring passing run read pools before amendment. Therefore the next Practice Management pass must make pool inspection the first visible substrate-authoring move, not a remembered prerequisite. At the moment a pass considers `pm_reload_seed_substrate`, `pm_check_documentation_impact`, any `pm_create_*` or `pm_amend_*` authoring material, invariant or evaluation material, or `pm_amend_bundle`, it must first ask: which pool surface supplies the ids or current content this action relies on? If that surface has not already been exposed by `pm_read_pool` in this enactment, invoke `read_pool` / `pm_read_pool` for that exact pool immediately and only then continue. If no exact pool can be named, or the pool read cannot be reached, record that as a substrate-surface blocker and do not proceed to reload, documentation-impact, authoring, amendment, evaluation, invariant, or bundle-wiring from memory, prior trail, or bundle-description text alone.

Author data, never code, wherever the substrate lets you. An evaluation spec is data: it declares generic signal *kinds* (affordance_coverage, outcome_presence, shape_repetition, recurring_summary_marker) parameterised for one practice, plus an `objective_ref` and a prose body. It is run by the one generic engine; you do not write the engine. A good spec is *traceable to the practice's teleo-affective objective* — its `objective_ref` names one of the practice bundle's teleo-affective ids so the evaluator demonstrably measures what the practice is *for* rather than something incidental. A spec that names no objective, or one that is not the bundle's, is a vacuous evaluator and is itself a friction. Where a practice is genuinely not yet measurable, say so honestly in the spec body rather than authoring a hollow measure. Authoring a spec does not activate it — wire its id into the bundle's `evaluation_ids` so the engine and routing pick it up.

Verify what you author where it is actually projected. An affordance, material, or evaluation authored into another bundle is not thereby projected into the authoring practice; it cannot be exercised — and so cannot be confirmed — by invoking it in place. Such a call fails with 'no affordance … in this practice', and that failure is not evidence the authoring was wrong, only that the check was aimed at the wrong projection: the thing lives on the bundle it was wired into, not on the one you are authoring from. To confirm a newly authored capability functions, exercise it on the bundle that carries it. Do not close an authoring enactment treating the change as confirmed when the only check could never have been projected here.
