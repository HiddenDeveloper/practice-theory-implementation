---
id: rule_pm_read_pool_before_authoring
name: Read the target pool before authoring
---
Before creating or amending any substrate element from Practice Management, invoke `read_pool` / `pm_read_pool` for the pool whose entries will be created, amended, or selected. For bundle amendments, read every pool whose ids are being added, removed, or relied on before `amend_bundle`; for affordance or material changes, read the affordance or material pool before authoring or amending. A seed reload, documentation-impact check, filesystem lookup, or successful author/amend result does not substitute for the explicit current-pool inspection, because the practitioner must see the current ids and content before changing the substrate. If the needed pool cannot be read, record that surface gap and stop instead of authoring from memory.

Treat this as the first grounding gate for Practice Management work whose purpose is substrate management, not as an optional pre-write reminder. When the task is to create, amend, wire, reload in support of, or check documentation impact for a substrate change, start by asking which current substrate pool or bundle surface the work depends on and invoke `read_pool` / `pm_read_pool` for that surface before using reload, documentation-impact, authoring, amendment, or bundle-selection steps as the working basis. `reload_seed_substrate` may refresh the server, and `check_documentation_impact` may inspect downstream documentation, but neither records the current substrate entries the practitioner is about to rely on. If an enactment has already used reload or documentation-impact while doing substrate-management work and has not yet read the relevant pool, backfill `pm_read_pool` before the first write; if the work cannot proceed from a current-pool read, record the blocker and stop.

For Friction 626's confirmed `uses_substrate_authoring_surface` quality concern, treat the five-of-eight missing-window pattern as active Practice Management drift even when individual write shapes are also guarded by deterministic invariants. A Practice Management substrate-stewardship enactment must make `pm_read_pool` visible before `pm_reload_seed_substrate`, `pm_check_documentation_impact`, `pm_create_*`, `pm_amend_*`, or `pm_amend_bundle`; if the pass has already begun with one of those materials and no pool read is present, the next move is not another reload, write, or documentation check, but a backfilled `pm_read_pool` for the relied-on pool or an explicit surface-gap blocker. Passing comparison enactments in the same evaluation window show the surface is available, so closure without that read should be treated as unfinished stewardship rather than acceptable variation.

For Friction 620's rerun `uses_substrate_authoring_surface` quality concern, treat repeated omission across the eight-enactment window as active practitioner drift: a Practice Management substrate-stewardship pass is not ready to invoke `pm_reload_seed_substrate`, `pm_check_documentation_impact`, `pm_create_*`, `pm_amend_*`, or `pm_amend_bundle` until the current enactment has a visible `pm_read_pool` for the pool surface the pass will rely on. Before the first stewardship material, explicitly choose the relevant pool from the intended change: `affordances` before creating or amending affordances, `materials` before material changes, `rules` / `understanding` / `teleo_affective` before conduct or intent edits, and the pools whose ids are selected or relied on before bundle wiring. If the pass began with reload or documentation impact and no pool read is present, stop the momentum, backfill the relevant `pm_read_pool`, and only then continue; if the relevant surface cannot be determined or read, record that blocker instead of closing as successful stewardship.

For Friction 612's confirmed `uses_substrate_authoring_surface` quality concern, make the pool-read gate an explicit before-first-step checklist for every Practice Management substrate-stewardship pass. If the intended pass includes reload, documentation-impact checking, authoring, amendment, or bundle wiring, first name the substrate surface being relied on and invoke `pm_read_pool` for the relevant pool before any stewardship material. If reload or documentation impact has already happened without that read, do not treat the pass as complete and do not proceed to a write from memory; immediately backfill the relevant `pm_read_pool`, or record the unreadable surface as a blocker and stop. Contrasting enactments that did perform `pm_read_pool` show the surface is available, so omission is practitioner drift to correct at the practice surface, not a reason to weaken the quality signal.

For Friction 602's refreshed `uses_substrate_authoring_surface` concern, Practice Management should treat the pool-read gate as an enactment-start checklist for every substrate stewardship pass, including reload-only, documentation-impact, authoring, amendment, and bundle-wiring work. Before the first stewardship material, identify the pool surface the pass will rely on and invoke `pm_read_pool`; if the first step was already reload or documentation impact, immediately backfill the relevant pool read before continuing to any authoring, amendment, bundle-selection, or closure. A pass that cannot identify or read the relevant pool should stop with a surface-gap/blocker rather than completing as if reload, documentation impact, or successful persistence had supplied current substrate inspection.

For the confirmed `uses_substrate_authoring_surface` quality concern in Friction 580, treat a sequence of `reload_seed_substrate` followed by `pm_create_affordance` and `pm_amend_bundle` with no earlier `pm_read_pool` as unfinished Practice Management, even when the created affordance and bundle amendment themselves persist. The required recovery is not another reload or documentation check: before the first write, read the affordance pool for the new affordance id and read the selected pools whose ids the bundle amendment will rely on. Reload-only or documentation-check-only enactments may need separate documentation stewardship, but they are not by themselves the authoring-without-pool-read case this rule governs; the conduct failure is the substrate write made from reload/memory rather than a current pool read.

Friction 584 confirms the same concrete authoring shape in enactment 8367059f-db1e-4e9e-b5fc-5528b101e612: `reload_seed_substrate` followed by `pm_create_affordance` for `read_morning_site_list` and `pm_amend_bundle` for `morning_briefing`, with no current-enactment `pm_read_pool`. Even when a quality window also flags reload-only or documentation-check trails, this write sequence is a genuine substrate-authoring failure. The Practice Management response is to make `pm_read_pool` precede the first authoring or bundle-selection write in the same enactment; a later reload, successful persisted write, or documentation check does not repair the missing pre-write substrate inspection.

This amendment responds to Friction 527's confirmed quality concern for Practice Management signal `uses_substrate_authoring_surface`: recent substrate-management enactments repeatedly used reload, authoring, bundle amendment, and documentation-impact surfaces without `pm_read_pool`. The added gate makes the required current-pool inspection the start-of-work grounding move for substrate management, so practitioners do not treat reload or documentation checks as substitutes for reading the substrate they are changing or relying on.

Friction 635 confirms the quality concern is still live across the evaluated window: five of eight recent Practice Management enactments lacked `pm_read_pool`, and the newest inspected enactment again used `pm_reload_seed_substrate`, `pm_create_affordance`, and `pm_amend_bundle` without a current pool read. Treat that pattern as a mandatory immediate-next-action rule for every Practice Management substrate-stewardship pass: the first write-shaped or reload-shaped move is not allowed to carry the pass forward unless `pm_read_pool` for the relied-on pool has already appeared in the current enactment. If a pass begins with reload anyway, the very next move must be the relevant `pm_read_pool`; if a write has already occurred without that read, stop further substrate action and record the missing pool-read blocker instead of treating persistence, invariants, or later documentation impact as closure.

Friction 639 confirms the same quality signal remains a genuine Practice Management practice concern after rerun: the evaluated window still had five of eight enactments missing `pm_read_pool`, and the grounded authoring example was again `pm_reload_seed_substrate` followed by `pm_create_affordance` for `read_morning_site_list` and `pm_amend_bundle` for `morning_briefing` with no pool inspection. Do not let reload-only or documentation-only missing examples blur the authoring gate: when the pass will create, amend, or wire substrate, the relevant `pm_read_pool` must be visible before the first write or bundle-selection step; if the pass is only reload or documentation stewardship, it must either read the substrate surface it relies on before treating the stewardship as complete, or explicitly record that no authoring/wiring is being performed and name the narrower surface gap or limit. The confirmed failure to fix is the practitioner carrying substrate-authoring momentum from reload, documentation, or memory into writes without first inspecting the current pool.
