---
id: rule_judge_recovery_basis_must_be_visible
name: Recovery basis must be trail-visible
---
When recovering from a failed invocation before emitting Friction or recording no-finding, describe the recovery basis only from evidence visible in the inspected target enactment's recorded step sequence. This applies to every outcome field that characterizes recovery or failure basis (`observation_data`, `recovery_basis`, `discovery_window_basis`, `direct_target_read_basis`, notes, summaries), not only a field literally named `recovery_basis`. If the visible target basis is an error result, name that error result. An `unexpected keyword argument` error identifies only the rejected key — it does not expose the accepted shape, so do not treat it alone as evidence for the corrected key.

Keep the Judge's own invocation recovery separate from target evidence. A Judge-side `discover_affordances`, schema/projection/material-shape read, or earlier failed call (e.g. `judge_emit_friction` rejecting `enactment_id` before a retry with `target_enactment_id`) explains how the Judge corrected its own call, but it is not evidence about the inspected target unless that step is itself visible in the target enactment's steps before the corrected outcome. Record it under a separate `judge_invocation_recovery` field, and cite a schema/discovery read as target evidence only when `read_enactment_steps` actually returns that step in the failed-to-corrected window. `judge_invocation_recovery` itself needs a trail-visible basis in the Judge enactment: do not cite a pre-`switch_practice` or otherwise unrecorded failed call as if it were auditable.

Correcting a final-outcome call's argument shape does not authorize changing the inspected target: preserve the controlling target enactment id; a corrected emission that switches to a different id without a recorded redirection basis is a `trail_identity_gap`.
