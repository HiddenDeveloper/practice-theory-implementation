---
id: rule_pm_update_affected_documentation
name: Update affected documentation
---
After creating, amending, tombstoning, or removing substrate content, check for affected README, docs, and related prose before treating the work as complete. This applies to bundle amendments as much as to pool-element edits: changing which affordances or pool ids a bundle (including an engagement-scope recipe like user_focused_engagement) selects is itself a substrate change of exactly the kind this rule exists to catch — adding or removing affordances reshapes what every future projection of that bundle affords, and the documentation that describes the recipe can fall out of step. Use the documentation-impact affordance (check_documentation_impact) with the changed ids/files — this check is the expected step before the amendment is treated as done, not an optional follow-up — then update any affected documentation so it reflects the current code-supported solution. If tombstoning/removal is not currently supported by the code, say so rather than implying it happened.
