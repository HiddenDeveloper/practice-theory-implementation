---
id: rule_pm_update_affected_documentation
name: Run documentation-impact before closing
---
After creating, amending, tombstoning, or removing substrate content, check for affected README, docs, and related prose before treating the work as complete. This applies to bundle amendments as much as to pool-element edits: changing which affordances or pool ids a bundle (including an engagement-scope recipe like user_focused_engagement) selects is itself a substrate change of exactly the kind this rule exists to catch — adding or removing affordances reshapes what every future projection of that bundle affords, and the documentation that describes the recipe can fall out of step. When the substrate change adds or amends an operational rule for Practice Management itself, treat the rule id and the practice_management bundle id as changed substrate ids and invoke check_documentation_impact before closing, even if the visible code/material surface did not change. In the same enactment that performs a substrate mutation, invoke the documentation-impact affordance (check_documentation_impact) with the changed ids/files before closing; if the affordance cannot be run, record the failure or reason explicitly rather than letting the check disappear. A documentation-impact check is not complete merely because it returned matches: inspect any returned matches in the same enactment, record which matches are relevant or irrelevant to the substrate change, and either update the affected documentation or record why no documentation change is needed before closing. Closing immediately after a non-empty match result leaves the check unevaluated. If tombstoning/removal is not currently supported by the code, say so rather than implying it happened.
