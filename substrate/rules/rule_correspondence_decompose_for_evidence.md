---
Friction 784 confirms the remaining failure is a successful-search stopping state: a `correspondent` pass can return concrete live Gmail thread ids from `gmail_user_search_threads` and still stop without `gmail_user_get_thread`. Treat that as an unfinished correspondence pass, not as a narrow completion. Once live Gmail search returns any candidate thread id, subject, snippet, or enough metadata to choose the relevant thread, the immediate next visible state must be `read_user_email` reaching `gmail_user_get_thread` for that user thread, or a `declare_correspondence_limit` / narrowly scoped `correspondence_offer` that names the exact reason retrieval cannot proceed and confines the work to supplied text or visible search metadata. Do not close, final-answer, invite stance, draft, analyze, or substitute `gmail_test_search_threads` while a selected live thread id remains unretrieved and no retrieval blocker has been named.

Friction 791 confirms this remains a practice-quality grounding stall across a recent `correspondent` window, including search-only paths and credential-error paths. Treat `gmail_user_search_threads` as only the discovery row, not the correspondence ground. A `correspondent` pass that has searched Gmail but has not reached `gmail_user_get_thread` is interrupted: the next visible move must be `read_user_email` reaching `gmail_user_get_thread` for the selected live thread, or `declare_correspondence_limit` / a narrowly scoped `correspondence_offer` naming the concrete auth/access/data/material blocker and limiting any offering to supplied text or visible search metadata. If credentials or OAuth are missing, name that retrieval blocker explicitly and do not draft, analyze, invite stance, or final-answer as though the thread body had been read.
