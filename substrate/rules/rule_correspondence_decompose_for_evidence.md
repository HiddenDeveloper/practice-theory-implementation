---
id: rule_correspondence_decompose_for_evidence
name: Decompose for evidence
---
Whether reading an incoming message or drafting an outgoing one, decompose the content into factual claims, stances, and commitments. For each, locate the evidence that grounds it. Claims from the sender are the sender's account until confirmed. Claims the user has not supplied, and commitments the user has not authorized, do not enter the draft as the user's voice.

When correspondence work begins from Gmail search results, the search result is only an index into the relationship surface, not the evidence itself. If `read_user_email` reaches `gmail_user_search_threads` and returns candidate threads or an access/auth/data error, the next correspondence move must either retrieve the relevant thread with `gmail_user_get_thread` in the same enactment before offering analysis or a draft, or explicitly name the retrieval/access gap and limit the response to what the search metadata or supplied message can support. Do not close a correspondence answer from search results alone while implying the thread has been read; if retrieval is unavailable, invite the user's stance or declare the correspondence limit instead of drafting from ungrounded thread context.

For the quality signal `grounds_correspondent_before_offering`, treat retrieval-before-offering as an operational gate. Before any `correspondence_offer`, draft proposal, analysis of thread substance, or reply wording that depends on an email thread, the current enactment must contain `read_user_email` reaching `gmail_user_get_thread` for the relevant thread, unless the user supplied the full message content directly or the practitioner explicitly names a search/auth/access/data retrieval gap and limits the offer to that narrower basis. A Gmail search step by itself is not enough evidence for a correspondence offer. If search succeeds, retrieve the thread before offering; if search or retrieval fails, do not offer grounded reply language or thread analysis as though the thread were read. Instead, state the limitation, invite the user's stance, or declare the correspondence limit.

Friction 624 confirms the remaining failure mode is closure after a Gmail search or Gmail access error with no thread retrieval and no explicit correspondence limit. After `read_user_email` reaches `gmail_user_search_threads`, a correspondent enactment is not ready to close on thread-dependent work until one of these is visible in the same enactment: `read_user_email` reaching `gmail_user_get_thread` for the selected thread, or a `declare_correspondence_limit` / `correspondence_offer` limit that names the search/auth/access/data retrieval gap and confines the answer to supplied text or visible search metadata. If search returns candidate thread ids, retrieve the relevant thread before any analysis, draft, or final answer about the thread. If Gmail auth, refresh-token, access, or material failure prevents retrieval, record that gap as the correspondence limit rather than leaving the trail as a search-only pass.

Friction 648 confirms the gate is still being missed in three of five recent correspondent enactments: practitioners searched or attempted correspondence access, including `gmail_user_search_threads` and test-search recovery, but did not retrieve the user thread with `gmail_user_get_thread` before offering correspondence stance, limits, or reply work. Treat the first Gmail search result or Gmail search/access error as a branch point, not as sufficient grounding. If candidate thread ids or enough metadata to identify the likely thread are visible, the immediate next correspondence-grounding move is `read_user_email` reaching `gmail_user_get_thread` for that thread before any `invite_correspondence_stance`, `correspondence_offer`, draft, thread analysis, or final reply wording. If the search/auth/access/material result prevents choosing or retrieving the thread, make that gap explicit through `declare_correspondence_limit` or a narrowly limited `correspondence_offer` before closing; do not substitute another search, a test-search attempt, or ungrounded stance invitation for thread retrieval. The trail should show one of two post-search outcomes in the same enactment: retrieved thread evidence, or a named retrieval/access gap that constrains the correspondence work.

Friction 684 confirms this branch-point rule still did not consistently shape the next move: in a fresh quality window, one pass received a Gmail thread snippet from `gmail_user_search_threads` and did not follow with `gmail_user_get_thread`, while two other passes encountered Gmail authorization errors before retrieval. Therefore, after any `read_user_email` / `gmail_user_search_threads` result, including a successful snippet, candidate thread id, refresh-token failure, OAuth/client-secret failure, access error, or test-search recovery attempt, pause before any stance invitation, correspondence offer, draft, thread analysis, reply wording, or final answer. The immediate next visible state must be one of: `read_user_email` reaching `gmail_user_get_thread` for the relevant thread; `declare_correspondence_limit` naming the exact search/auth/access/data/material gap; or a narrowly scoped `correspondence_offer` that says it is based only on supplied message text or visible search metadata. Do not let search-only evidence, a second search, a test material, or an implicit auth failure stand in for full reachable thread context.
