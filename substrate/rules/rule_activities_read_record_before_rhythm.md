---
id: rule_activities_read_record_before_rhythm
name: Backfill recent activity before rhythm from detail or daily summary
---
For the quality signal `reads_activity_record_before_describing_rhythm`, the expected first grounding move is explicit: before any `activities_management` answer describes or probes activity rhythm, weekly pattern, completed activity mix, gaps, streaks, cadence, or "what was done," invoke `recent_activity` reaching `garmin_list_activities` for the relevant recent window, unless the answer is explicitly confined to one supplied isolated activity id/date or the list read has an auth/data/material gap that is named and treated as limiting the answer.

When activity work turns toward rhythm, frequency, gaps, week pattern, or "what was done," the required grounding move is `recent_activity` / `garmin_list_activities` before the final rhythm description. This is an operational gate, not background advice: at the start of an `activities_management` pass, if the likely answer will describe recent activity rhythm, weekly pattern, completed activity mix, gaps, streaks, or training cadence, first read `recent_activity` / `garmin_list_activities` for the relevant recent window before using detail, daily-summary, route, GPS-shape, IWT-analysis, or visualization surfaces. Coverage for this gate means a current-enactment `recent_activity` affordance invocation reaching `garmin_list_activities`; activity detail, daily summary, route, GPS-shape, IWT-analysis, visualization, or stale-material recovery steps do not satisfy the coverage signal by themselves. If the request is ambiguous between a single isolated record and a broader activity-record/rhythm answer, default to the list read first; narrow Garmin reads are allowed first only when the user explicitly asks about one supplied activity id/date and the answer will stay confined to that isolated record. Before finalizing any rhythm, week-pattern, or "what was done" answer, check the trail for a successful `garmin_list_activities` step in the current enactment; if it is absent, either perform that read then answer from it, or explicitly name the auth/data/material gap and limit the answer to the isolated record available. This remains true even when the pass began from an activity id, activity detail, or daily wellness date: if `activity_detail` / `garmin_get_activity`, `daily_summary` / `garmin_get_daily_summary`, route analysis, GPS shape, or visualization has been used first and the answer will describe rhythm or week-pattern, immediately backfill `recent_activity` / `garmin_list_activities` for the relevant recent window before answering. If a stale Garmin material alias fails, use the projected affordance surface to recover the current material name; that recovery does not replace the required `recent_activity` / `garmin_list_activities` grounding whenever the answer concerns recent activity, week pattern, rhythm, or what was done. Detail and daily summary can deepen or contextualize the list; they cannot stand in for the activity record list. If the list cannot be read because of auth, data, or material access, name that gap explicitly and limit the answer to what the isolated record supports.

Friction 566 confirms that this failure pattern is still occurring specifically through `activity_detail` / `garmin_get_activity` and `daily_summary` / `garmin_get_daily_summary`: those adjacent Garmin reads are evidence supplements only. If either has been used and the answer will characterize recent activity rhythm, weekly pattern, completed activity mix, gaps, streaks, cadence, or what was done, the practitioner must treat the missing current-enactment `recent_activity` / `garmin_list_activities` step as unfinished grounding, perform the list read before answering, or explicitly name the list/auth/data/material gap and constrain the answer to the isolated record.

Friction 578 confirms the remaining failure mode is not only wrong material selection but one-step closure: an `activities_management` enactment that performs only `activity_detail` / `garmin_get_activity`, only `daily_summary` / `garmin_get_daily_summary`, or a failed stale Garmin alias call has not completed the rhythm-record grounding when the answer concerns recent activity, week pattern, activity mix, gaps, cadence, or "what was done." After any such narrow or failed first step, the practitioner must recover through the projected affordance surface if needed and then invoke `recent_activity` / `garmin_list_activities` in the same enactment before offering the rhythm description. If that list read cannot be reached or returns an auth/data/material gap, the answer must say so and stay confined to the isolated detail or daily wellness evidence; it must not present a broader rhythm from the narrow step alone.

This amendment responds to Friction 549 by making the coverage expectation for the confirmed quality signal front-loaded and unmistakable: the first grounding move for rhythm, week-pattern, completed activity mix, gaps, streaks, cadence, or "what was done" is `recent_activity` / `garmin_list_activities`, with only the isolated-record and explicit-gap exceptions above. The prior Friction 543 amendment remains in force: the activity-record coverage signal is satisfied only by `recent_activity` / `garmin_list_activities` or by an explicit list/auth/data/material gap, not by adjacent Garmin reads or stale-alias recovery.

Friction 610 confirms that even after the affordance-level warnings, recent passes are still closing from `activity_detail` / `garmin_get_activity`, `daily_summary` / `garmin_get_daily_summary`, or stale-alias recovery without the activity-record list. Treat the coverage gate as a pre-final checklist, not only a first-move preference: before any final answer that describes activity rhythm, weekly pattern, completed-activity mix, gaps, streaks, cadence, or "what was done," verify that the current enactment contains `recent_activity` reaching `garmin_list_activities`. If it does not, the answer is not ready. Invoke the list read immediately, or explicitly state the list/auth/data/material gap and restrict the answer to the isolated activity or daily wellness evidence already read. Do not let a successful detail or daily-summary read, or a recovered stale material alias, be presented as completion for the broader activity-record/rhythm question.

Friction 629 confirms the miss persists across most of a recent evaluated window even when the bundle description already names `recent_activity` / `garmin_list_activities` as the entry grounding move. Therefore, after any `activity_detail` / `garmin_get_activity`, `daily_summary` / `garmin_get_daily_summary`, route, GPS-shape, IWT-analysis, visualization, or stale adjacent Garmin alias step, pause before any further synthesis or additional adjacent probing and classify the pass: if the answer will remain strictly confined to one supplied isolated activity id/date or one daily wellness snapshot, say that limit; otherwise the immediate next grounding move must be `recent_activity` / `garmin_list_activities` for the relevant recent window. A later final-answer checklist is not enough if the pass has already drifted into detail-first elaboration; the backfill belongs immediately after the first adjacent read that reveals the work is broader than an isolated record.

Friction 679 confirms this is still a repeated coverage gap across a fresh evaluated window, with four passes using `activity_detail` / `garmin_get_activity`, `daily_summary` / `garmin_get_daily_summary`, or stale adjacent Garmin starts before any `recent_activity` / `garmin_list_activities` grounding while a contrast pass succeeded by invoking the list first. In future `activities_management` passes, treat the first adjacent detail or daily-summary step as an interruption point: before another Garmin read, synthesis, or final answer, either backfill `recent_activity` / `garmin_list_activities` for the relevant recent window, or explicitly record that the work is confined to one supplied isolated activity/date or blocked by a concrete list/auth/data/material gap. The practitioner should not proceed from adjacent Garmin evidence into rhythm, week-pattern, completed-activity mix, gaps, streaks, cadence, or "what was done" language until that list-grounding state is visible in the same enactment.

Friction 692 confirms the same gate is still being missed after another quality review: four of five evaluated passes used `garmin_get_activity`, `garmin_get_activity_detail`, `garmin_get_daily_summary`, or stale daily-summary/detail material paths without `garmin_list_activities`, while a neighboring pass showed the list was reachable. The next `activities_management` pass that touches any adjacent Garmin detail, daily summary, route, GPS-shape, IWT-analysis, visualization, or stale Garmin alias must make the activity-record state visible before proceeding: either `recent_activity` / `garmin_list_activities` has already succeeded in the current enactment, it is invoked immediately as the next grounding move, or the pass explicitly names a concrete list/auth/data/material blocker and confines the answer to the isolated activity or daily wellness snapshot. Do not continue with additional adjacent Garmin reads, rhythm synthesis, week-pattern language, completed-activity-mix claims, gaps/streaks/cadence claims, or final answer prose while that list-grounding state is absent.
